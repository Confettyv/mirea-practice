# Архитектурные и алгоритмические решения (Практическая работа №6)

### Решение 1. Строгая иерархия условий через ранний выход (Guard Clauses)
В методе `ApprovalRouter.route` применён паттерн Guard Clauses (ранний возврат `return` при первом совпадении критерия) с упорядочением проверок от наиболее критических к общим:
1. Персональные данные (`SECURITY_REVIEW`)
2. Критический риск (`DIRECTOR_REVIEW`)
3. Превышение финансового порога (`FINANCE_REVIEW`)
4. Срочность при допустимом бюджете (`FAST_TRACK`)
5. По умолчанию (`STANDARD`)
Это исключает вложенные конструкции `if-else` глубиной более двух уровней, устраняет неоднозначность пересекающихся условий и гарантирует соблюдение приоритетов бизнес-правил.

### Решение 2. Инкапсуляция порогового лимита и явная валидация входных данных
Порог финансового контроля вынесен в атрибут экземпляра `financeLimit` с инициализацией через конструктор по умолчанию (константа 500 000). Это изолирует бизнес-правило Варианта 1 в единственном месте без размазывания числовых литералов по методам. Валидация входных данных (`amount < 0`, `riskLevel == null`) вынесена в приватный метод `validateInput`, предотвращая передачу повреждённого состояния в логику принятия решений.
