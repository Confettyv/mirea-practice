# Принципиальные архитектурные решения проекта

### Решение 1. Отказ от хранения поля `total` в пользу динамического вычисления
- **Контекст:** Итоговая сумма заказа может быть сохранена как числовое поле `private double total` либо рассчитываться на лету через вызов `total()`.
- **Решение:** Поле `total` не заводится. Метод `total()` вычисляет сумму строк заказа (`OrderItem.getLineTotal()`) в момент обращения.
- **Обоснование:** Хранение вычисляемого поля порождает риск рассинхронизации данных при добавлении, изменении количества или удалении позиций. Динамический расчет исключает дублирование состояния и гарантирует 100% актуальность суммы при любых модификациях состава заказа.

### Решение 2. Инкапсуляция коллекции `items` через `Collections.unmodifiableList`
- **Контекст:** Геттер `getItems()` должен предоставлять доступ к списку позиций для чтения и отображения в отчетах.
- **Решение:** Метод возвращает `Collections.unmodifiableList(items)` вместо оригинального списка.
- **Обоснование:** Прямой возврат ссылки на `items` позволил бы внешнему коду добавлять или удалять позиции без валидации бизнес-правил (в обход статуса `CONFIRMED` и проверки лимитов количества). Неизменяемая обертка делает состояние заказа защищенным от стороннего вмешательства.
